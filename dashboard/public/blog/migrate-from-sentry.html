We Replaced Sentry in 10 Minutes — Here's How (Drop-In Migration Guide)

Adrian Elder·February 21, 2026·10 min read

If you're looking to migrate from Sentry, I have good news: it's the fastest platform migration you'll ever do.

Most migration guides are full of warnings about re-instrumentation, SDK changes, data model differences, and weeks of parallel running. Migrating to Moneat is none of those things. You change one line of code per service — the DSN — and you're done.

This guide walks through exactly how to do it, in the order you'd actually do it.

Why Teams Migrate from Sentry

Before the how, let's quickly cover the why — because the reason shapes the migration plan.

The most common reasons teams switch:

  1. Cost — Sentry's Team plan includes 50K errors/month. Growing apps hit overages fast, and the overage math is brutal (about $0.000188/error at mid-volumes — meaning $188 for every million errors over quota).

  2. Data ownership — Sentry's cloud is US-based. For teams with GDPR obligations, EU users' exception data and session replays flowing to US servers creates compliance headaches.

  3. Feature gaps — Sentry doesn't offer status pages, on-call/incident management, infrastructure monitoring, or LLM observability. Teams end up paying for Sentry + Statuspage.io + PagerDuty + something else.

  4. Self-hosting — Sentry's self-hosted version exists but is notoriously resource-hungry (20+ Docker services, significant memory requirements). Teams want a lighter self-hosted option.

Moneat addresses all of these while remaining fully compatible with every Sentry SDK.

How the Compatibility Works

Moneat implements the Sentry envelope ingestion protocol — the same HTTP API that Sentry SDKs use to send data to ingest.sentry.io. Every Sentry SDK (JavaScript, Python, Kotlin, Swift, Ruby, Go, PHP, Java, .NET, Elixir, and more) sends events to Moneat exactly as it would to Sentry.

Step 1: Set Up Your Moneat Instance (5 minutes)

Option A: Moneat Cloud

Sign up at moneat.io. Create an organization, then create a project. Moneat generates a DSN for the project that looks like:

https://{public_key}@app.moneat.io/api/{project_id}

Done. Skip to Step 2.

Option B: Self-Hosted (10 minutes)

If data residency or cost is your motivation, self-hosting is the path.

Requirements:

  • Docker and Docker Compose
  • A server with at least 2 GB RAM (4 GB recommended for production)
  • A domain name (for SSL)
# Clone the repo
git clone https://github.com/moneat/moneat
cd moneat

# Copy and edit the environment file
cp .env.example .env

Edit .env with your values:

# Required
JWT_SECRET=your-long-random-secret-here
DATABASE_PASSWORD=your-postgres-password
CLICKHOUSE_PASSWORD=your-clickhouse-password
FRONTEND_URL=https://moneat.yourdomain.com
BACKEND_URL=https://api.yourdomain.com

# Optional: SMTP for email alerts
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=alerts@yourdomain.com
SMTP_PASS=your-smtp-password

# Start the stack
docker-compose up -d

# Check that everything's running
docker-compose ps

Point your domain's DNS at the server, configure nginx/Caddy for SSL, and you have a production Moneat instance. The full self-hosting guide is at moneat.io/docs/self-hosting.

Step 2: Create Your Projects and Get DSNs (2 minutes)

In the Moneat dashboard:

  1. Go to Settings → Projects
  2. Click New Project
  3. Select your platform (JavaScript, Python, etc.) — or just pick "Other" for any Sentry SDK
  4. Copy the generated DSN

The DSN format is: https://{key}@{host}/api/{project_id}

Create one project per Sentry project you're migrating.

Step 3: Update Your SDKs (The Only Code Change)

This is the entire code migration. Find your Sentry initialization and update the dsn value.

JavaScript / TypeScript

// Before
import * as Sentry from "@sentry/browser";

Sentry.init({
  dsn: "https://abc123@o456789.ingest.sentry.io/123456",
  tracesSampleRate: 1.0,
  replaysSessionSampleRate: 0.1,
});

// After — only this line changes
Sentry.init({
  dsn: "https://abc123@moneat.yourdomain.com/api/1",
  tracesSampleRate: 1.0,
  replaysSessionSampleRate: 0.1,
});

Python

# Before
import sentry_sdk
sentry_sdk.init(
    dsn="https://abc123@o456789.ingest.sentry.io/123456",
    traces_sample_rate=1.0,
)

# After
sentry_sdk.init(
    dsn="https://abc123@moneat.yourdomain.com/api/1",
    traces_sample_rate=1.0,
)

Step 4: Configure Source Maps (Optional but Recommended)

If you upload source maps to Sentry for readable JavaScript stack traces, you'll want to do the same with Moneat. The CLI is compatible:

# Install sentry-cli if you haven't already
npm install -g @sentry/cli

# Configure to point at Moneat instead of Sentry
export SENTRY_URL=https://moneat.yourdomain.com
export SENTRY_AUTH_TOKEN=your-moneat-auth-token
export SENTRY_ORG=your-org-slug
export SENTRY_PROJECT=your-project-slug

# Upload source maps (same command as before)
sentry-cli releases files "$RELEASE" upload-sourcemaps ./dist

Step 5: Set Up Alerts (5 minutes)

Moneat has its own alert system in Settings → Alerts. Create rules for:

  • Error threshold — alert when a new issue is first seen
  • Error rate spike — alert when errors exceed a threshold in a time window
  • Uptime — configure uptime monitors to ping your endpoints

Connect to Slack, email, PagerDuty, or Moneat's built-in on-call system.

Step 6: Validate Everything Is Working

After deploying with the new DSN:

  1. Trigger a test error in your app (throw an exception in a dev environment)
  2. Check the Moneat Issues dashboard — the error should appear within seconds
  3. Verify stack traces are readable (check source maps if not)
  4. Check that user context, tags, and breadcrumbs are showing up correctly

If you're using session replay, open your app in a browser, navigate around, and check Replays in the Moneat dashboard.

What About Historical Data?

Moneat doesn't import historical Sentry data. This is almost always fine — error monitoring data has a short half-life, and teams rarely need to reference errors from 60+ days ago.

If you need historical data for compliance or trending, export it from Sentry before canceling your plan. Sentry supports data exports via their API.

Practical recommendation: Run both Sentry and Moneat in parallel for 1–2 weeks before canceling Sentry. This is easy since you can simply update the DSN in one service at a time, or configure your SDK to send to both:

// Temporarily send to both during transition
Sentry.init({
  dsn: "https://abc123@moneat.yourdomain.com/api/1",
});
// Keep old Sentry project active to catch anything you missed

What People Get Wrong About Migrating from Sentry

  • "Migrating error monitoring tools takes weeks." With Sentry SDK-compatible platforms, the actual code change is one line per service (the DSN). The total migration for most apps is under an hour, not weeks.

  • "I need to wait for a clean break between projects." You don't. Since the DSN is per-project, you can migrate one service at a time. Run Sentry and the new platform in parallel during the transition with zero conflict.

  • "My existing Sentry alert rules will carry over." They won't — alert configurations are platform-specific. Budget 10-15 minutes to recreate your most critical alerts in the new platform.

  • "Session replay won't work without code changes." If you're already using @sentry/replay, session replay works immediately with any Sentry-compatible backend. The replay SDK sends data through the same envelope protocol as errors.

  • "I'll lose my historical data." You won't have historical data in the new platform, but error monitoring data has a short half-life. Teams rarely reference errors older than 30 days. Run both platforms in parallel for 1-2 weeks if you need continuity.

Tradeoffs, Caveats, and Second-Order Effects

  • Sentry's Seer AI debugger has no equivalent in Moneat. If your team relies heavily on AI-assisted debugging, you lose that capability. The $40/active-contributor/month cost disappears, but so does the feature.

  • Profiling is a Sentry-only feature. Moneat does not support continuous profiling or profiling visualization. If profiling is core to your workflow, you'll need to keep Sentry for that use case or use a separate profiling tool.

  • Sentry's community ecosystem is larger. More StackOverflow answers, more third-party tutorials, more blog posts. Smaller platforms have smaller communities, which means more self-reliance for edge-case troubleshooting.

  • Self-hosted Moneat introduces operational responsibility. If you're migrating from Sentry Cloud to self-hosted Moneat, you're trading a managed service for infrastructure you maintain. Budget a few hours per month for updates and monitoring.

  • Older Sentry SDK versions (pre-v6) may have compatibility gaps. The envelope protocol is standardized in v6+. If you're on very old SDK versions, test thoroughly before committing.

  • Team familiarity has a cost. Engineers who know Sentry's UI will need 1-2 days to get comfortable with a new dashboard. This is minor, but non-zero.

Frequently Asked Questions

Does this work with @sentry/react, @sentry/nextjs, @sentry/node, etc.? Yes. All Sentry SDK packages work. Moneat receives data from any SDK that implements the Sentry envelope protocol.

Will my existing Sentry alert configurations work? No — alert configurations are platform-specific and need to be recreated in Moneat's alert settings. This takes about 10 minutes.

What about Sentry's AI debugger (Seer)? Moneat doesn't replicate Seer specifically, but offers its own error grouping, similar issue aggregation, and stack trace rendering. Seer on Sentry costs an additional $40/active contributor/month — a fee that disappears with Moneat.

Can I use Moneat for some projects and Sentry for others? Yes. The DSN is per-project. You can migrate projects one at a time.

What about SDK version compatibility? Moneat is tested against current Sentry SDK versions (v7, v8) across all major platforms. Older SDK versions (v6+) also work.
